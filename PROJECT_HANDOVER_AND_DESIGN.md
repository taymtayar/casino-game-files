## 1. Game Mechanics & Probabilities

"Double Down" is a two-stage casino game where players place an initial bet with the chance to win a 2x payout, or "Double Down" to try for even higher multipliers.

### Step 1: The Initial Bet
- **Payout:** 2.00x the initial bet amount.
- **Win Probability:** 47.50%
- **House Edge:** 5.00%
- **Flow:** 
  - The player places a bet (e.g., $1.00).
  - The game evaluates a random number between 0.0 and 100.0.
  - If the roll is under 47.50, the player wins the Step 1 phase and the current prize is $2.00.
  - If the player loses, the round is over, and the bet is lost.
- **Player Choice:** If the player wins Step 1, they are presented with two options:
  1. **Cashout:** Take the 2.00x payout.
  2. **Double Down:** Risk the 2.00x payout for a chance at a higher multiplier.

### Step 2: The Double Down
If the player chooses to Double Down, a second RNG event evaluates which tier they land on. The default result if they do not land on a winning tier is a **Bust (0x multiplier)**.

**Double Down Tiers & Probabilities:**
| Tier Name | Multiplier | Probability |
| :--- | :--- | :--- |
| **Bronze** | 2.50x | 20.00% |
| **Silver** | 3.50x | 10.00% |
| **Gold** | 5.00x | 5.00% |
| **Diamond** | 10.00x | 1.00% |
| **Bust** | 0.00x | 64.00% (Implied) |

*Note: The multipliers are applied to the **original base bet**, not the Step 1 payout.*

## 2. Provably Fair RNG System

The RGS implements a strict, industry-standard Provably Fair algorithm using **HMAC-SHA256**, ensuring that the casino cannot manipulate the outcome and the player can independently verify the results.

1. **Server Seed:** A secure, cryptographically random hex string generated by the server. It is kept hidden from the player until the round concludes.
2. **Client Seed:** A user-provided string that influences the RNG.
3. **Nonce:** An integer that increments for every RNG event within a round.
   - `Nonce 0` is used for the Step 1 roll.
   - `Nonce 1` is used for the Step 2 roll.
4. **Generation Logic:** 
   - `HMAC_SHA256(serverSeed, clientSeed + "-" + nonce)`
   - We take the first 8 characters (4 bytes) of the resulting hex hash.
   - We convert it to a decimal integer and divide by `4294967295` (max 32-bit integer) to get a uniform float between 0.0 and 1.0.
   - We multiply by 100 to get a roll between `0.000` and `99.999`.

## 3. Seamless Wallet Integration (Stake & Hub88 Standard)

A critical requirement of this RGS is that it **does not hold player balances**. Instead, it acts as a stateless orchestrator, firing real-time, synchronous HTTP webhooks to the Casino Operator's Seamless Wallet API. 

This architecture guarantees that the casino platform maintains the source of truth for all financial transactions, meeting the exact standards required by operators like Stake and Hub88.

### Webhook Lifecycle
The RGS communicates with the operator via an HTTP client module (`walletService.js`). 

1. **Balance Check:** Prior to placing a bet, the UI can optionally fetch the balance.
2. **Debit (Bet Placement):** When the player clicks "Bet", the RGS immediately fires a `/debit` webhook to the casino operator to deduct the wager from the player's wallet.
3. **Credit (Win/Cashout):** If the player Cashes Out or hits a winning Double Down tier, the RGS fires a `/credit` webhook to add the winnings to the player's wallet.
4. **Rollback (Error Handling):** If a critical error occurs *after* a debit but before a round can be fully established, the RGS fires a `/rollback` webhook to refund the player automatically.

### Webhook Security (HMAC Signing)
To ensure the casino operator can trust the incoming webhooks, **every outbound request is signed** by the RGS.
- The RGS generates an HMAC-SHA256 hash of the JSON payload using a shared `OPERATOR_SECRET_KEY`.
- This signature is attached to the `X-Signature` HTTP header.
- The casino operator recalculates the hash using the same secret key and payload to verify authenticity.

## 4. Backend Architecture & Polish

**Tech Stack:** Node.js, Express, Redis.

### Stateful Operations via Redis
Because Node.js is stateless across horizontal scaling, the state of an active round is temporarily stored in Redis.
- When a bet is placed and Step 1 is won, the round data (seeds, bet amount, and pre-calculated Step 2 outcome) is cached in Redis with an expiration timer.
- When the player executes an action (Cashout or Double Down), the RGS validates the round against Redis.

### Audit Logging
Every completed round (a Step 1 loss, a Cashout, or a Double Down attempt) generates a permanent audit log stored in a Redis List (`global_game_history`). This provides an immutable trail of every transaction and RNG outcome for regulatory and dispute-resolution purposes.

### Critical Edge Cases Mitigated
During the final backend audit, two critical, industry-standard vulnerabilities were patched:

1. **The "Lost Wager" Crash Prevention:**
   If the Redis database crashes or a network failure occurs immediately after the `/debit` webhook succeeds, the player's wager is lost without a game round being created. 
   - **Fix Applied:** The core RNG and Redis caching logic is wrapped in a strict `try/catch` block. If the local processes fail, the `catch` block intercepts the failure and immediately fires a `/rollback` webhook to the casino operator, refunding the player before throwing a 500 error.
   
2. **The "Double Spend" Race Condition Prevention:**
   If a malicious user runs a script to fire two identical `/api/cashout` requests in the same millisecond, they could potentially trigger two `/credit` webhooks before the system deletes the round.
   - **Fix Applied:** The RGS utilizes an **atomic deletion check**. Inside the Cashout and Double Down endpoints, the RGS executes `await redisClient.del(round_id)`. Redis will return the number of keys deleted (`1` or `0`). If it returns `0`, it means a parallel request already deleted the round a millisecond prior, and the server immediately rejects the duplicate request, completely mitigating the double-spend vulnerability.

## 5. Local Development Setup

To run this backend locally, you will need **Node.js** and **Redis**. We recommend using Docker to run Redis easily without system-level installations.

### Prerequisites
- Node.js (v18+)
- Docker Desktop (for Redis)

### Step-by-Step Installation

1. **Start the Redis Database (via Docker)**
   Open a terminal and run the following command to spin up a local Redis container on the default port (6379):
   ```bash
   docker run -d --name igaming-redis -p 6379:6379 redis
   ```
   *Note: The RGS relies heavily on Redis for state and audit logging. The server will crash on startup if Redis is not running.*

2. **Install Node Dependencies**
   ```bash
   npm install
   ```

3. **Start the Mock Casino Operator**
   In a new terminal window, start the mock wallet server (simulates Stake/Hub88 APIs):
   ```bash
   node mockOperator.js
   ```

4. **Start the Game Server**
   In another terminal, start the main Remote Game Server:
   ```bash
   npm start
   ```
